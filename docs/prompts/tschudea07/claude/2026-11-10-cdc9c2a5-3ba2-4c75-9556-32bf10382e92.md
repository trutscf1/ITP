## Grundidee: zuerst Dokumentation, dann Tests, dann Code

Das Projekt läuft **documentation-first** (`documentation/MANIFEST.md`). Maßgeblich ist der Ordner `documentation/`, nicht der Code. Alles leitet sich von einem Ziel ab:

```
GOAL.md (G-1) → Konzept pro Feature → User Stories (US-n) → Acceptance Criteria (AC-n.m) → Tests → Code
```

Gesteuert wird das Ganze über den Skill `/engineering-human` (inzwischen umbenannt in `/gam-engineering`). Er ist der Router für alle Schritte: grill, tickets, implement, review, revise, merge, release.

Darüber stehen die Vorgaben eures Lehrers in `docs/`. Wenn sich die Regeln widersprechen, gilt `docs/`.

## Ablauf eines Features

**1. Konzept (Phasen 1–6 im Manifest)**
- Jedes Roadmap-Feature (R1–R14) hat ein Concept-Issue (`type::concept`) und einen eigenen Branch `concept/<feature>`.
- Der Owner „grillt“ das Feature mit `/engineering-human <feature>`. Dabei werden offene Fragen geklärt, Begriffe geschärft, Architektur und Vertical Slices festgelegt und das Testkonzept geschrieben, mit Tests pro AC-ID.
- Ergebnis ist ein Konzeptdokument in `documentation/concepts/` mit Status `ready`.

**2. Tickets**
- Mit `/engineering-human tickets <feature>` wird das Konzept in GitLab-Issues zerlegt: ein Feature-Issue, darunter Story-Issues, darunter Slices.
- Ein Slice soll in eine Projekteinheit passen, also 200 Minuten am Dienstag.
- Jedes Issue hat Acceptance Criteria, Weight (1/2/3/5/8), Assignee, Sprint-Milestone, genau ein `type::`-Label und genau ein `status::`-Label.

**3. Implementierung, test first (ADR-0005)**
- Der Branch `feature/<issue>-<slug>` oder `fix/<issue>-<slug>` wird vom aktuellen `dev` abgezweigt.
- Zuerst kommt ein Commit `test(<scope>): … [AC-ID]` mit fehlschlagenden Tests. Danach folgen `feat`/`fix`-Commits, bis die Tests grün sind.
- Commits folgen Conventional Commits mit Requirement-ID, zum Beispiel `fix(db): … [SCF-NF-6]`. commitlint prüft das im Hook und in der CI.
- Das zugehörige Konzeptdokument wird im **selben** MR aktualisiert, damit Code und Doku nicht auseinanderlaufen.

**4. Merge Request → Review → Merge**
- Ziel ist immer `dev`. Pro Story gibt es einen MR mit `Closes #<issue>`.
- Eine **andere Person** reviewt gegen die Acceptance Criteria und die Definition of Done (20 Punkte in `WORKFLOW.md`) und schreibt einen inhaltlichen Kommentar. Anmerkungen werden mit `/engineering-human revise` eingearbeitet.
- Vor dem Merge müssen die Pipeline grün und alle Threads resolved sein.
- Gemergt wird mit Merge-Commit, ohne Squash. Niemand merged seinen eigenen MR.
- Branches werden **nie gelöscht**, weil die Branch-Historie benotet wird. Das ist eine bewusste Abweichung vom Profil.

**5. Release am Sprintende**
- Ein Release-MR `dev` → `main` mit kuratiertem `CHANGELOG.md`. Den Entwurf erzeugt `pnpm run changelog:draft`.
- Danach ein annotierter Tag `v0.<sprint>.0`. Die CI erstellt daraus das GitLab-Release. Das finale Release ist `v1.0.0`.
- Zum Schluss werden die Status in `ROADMAP.md` aktualisiert.

**6. Regeneration-Probe**
Pro Sprint wird ein Feature in einem leeren Worktree nur aus Konzept und Tests neu generiert. Wenn dann Tests scheitern, fehlt etwas in der Doku, und das wird zuerst dort behoben.
