### 2. Answer (2026-11-03T13:39:04.264Z)

```text
Der Skill `engineering-human` ist euer festes Regelwerk für den ganzen Entwicklungsablauf. Er liegt im Repo unter `.claude/skills/engineering-human/` und gilt für alle im Team gleich. Laut `CLAUDE.md` beginnt jede Planungs-, Konzept- oder Umsetzungssitzung damit.

## Was er macht

**1. Er merkt sich Entscheidungen, die schon gefallen sind.**
In `PROFILE.md` stehen eure festen Entscheidungen mit IDs (`P-GIT-…`, `P-MR-…`, `P-VER-…`), etwa der Git-Flow mit `main` und `dev`, SemVer, die Merge-Regeln und die Definition of Done. Ein Agent fragt das nicht noch einmal, sondern nennt nur die IDs, die er anwendet.

**2. Alles leitet sich vom Projektziel ab.**
Die Kette ist: `G-1` in `GOAL.md` (höchstens 200 Zeichen) → Feature-Ziel → User Stories → Acceptance Criteria → Anforderungen → Code. Was dem Ziel nicht dient oder ihm widerspricht, wird gemeldet.

**3. Die Doku zuerst.**
`documentation/` ist die Wahrheit darüber, was das System tut. Ändert sich Code, wird das zugehörige Dokument im selben MR angepasst. Alles ist so geschrieben, dass Menschen und KI es lesen können (Part H ist die Zusammenfassung für Menschen).

**4. Der Arbeitsablauf ist nachvollziehbar.**
Jede Story ist ein Issue mit Acceptance Criteria und Gewicht. Jede Änderung läuft über einen MR, den eine andere Person reviewt. Der Status in `ROADMAP-DETAILS.md` und `ROADMAP.md` stimmt in dem Moment, in dem etwas auf `dev` landet.

**5. Teambetrieb.**
Jeder Entwickler hat seine eigenen Status- und Inbox-Dateien unter `documentation/team/<handle>/`, damit es keine Merge-Konflikte gibt.

## Die Befehle

| Befehl | Zweck |
| --- | --- |
| `/engineering-human` | Erkennt den Stand und macht dort weiter |
| `… <feature>` (grill) | Fragt ein Feature bis zum fertigen Konzept durch |
| `… tickets <feature>` | Macht aus den Stories Issues auf GitLab |
| `… implement <issue>` | Branch, Tests zuerst, Code, MR |
| `… review <MR>` | Prüft einen MR gegen die Acceptance Criteria und die Definition of Done (das habe ich gerade gemacht) |
| `… revise <MR>` | Arbeitet die Review-Kommentare zum eigenen MR ab |
| `… merge <MR>` | Mergt nach der Merge-Regel und aktualisiert den Status |
| `… release` | Release von `dev` nach `main` mit Tag und Release Notes |
| `… check` | Prüft die ganze Doku auf Widersprüche und veralteten Status |
| `… triage`, `wayfind`, `sweep` | Neue Issues einordnen, große Vorhaben planen, die Architektur prüfen |
| `… settings` | Merge-Einstellungen in `.claude/settings.json` ansehen oder ändern |

## Feste Regeln für Agenten

- **Jede Frage ist ein Pop-up** mit nummerierten Optionen, und die empfohlene steht oben. Jede Fragerunde wird in `qa-log.md` protokolliert.
- **Vor jedem Merge wird gefragt:** Bei euch steht die Merge-Regel auf `ask`, deshalb fragt der Agent vor jedem Merge per Pop-up. Zusätzlich lässt sich Claude Code `git merge` noch einmal bestätigen.
- **Nichts wird ungefragt veröffentlicht:** Kommentare, Issues und Releases auf GitLab werden vorher gezeigt und bestätigt.
- **Status-Hook:** Am Ende jeder Antwort mahnt ein Hook, falls nach einem Merge der Status nicht aktualisiert wurde.

Kurz gesagt baut der Skill also kaum eigene Werkzeuge. Er legt fest, *wie* die anderen Skills (`grilling`, `tdd`, `code-review` usw.) in eurem Projekt eingesetzt werden, damit Code, Doku und GitLab zusammenpassen.

In der Skill-Liste steht außerdem ein `humanengineering` mit fast derselben Beschreibung. Das ist vermutlich eine andere installierte Version, verbindlich für das Projekt ist aber die Kopie im Repo (`engineering-human`).
```
