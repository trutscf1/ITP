```text
wie funktioniert die Pipline die bei jedem pr durchläuft
```

### 2. Answer (2026-11-10T13:21:06.063Z)

```text
Die Pipeline ist eine **GitLab-CI-Pipeline**, definiert in `.gitlab-ci.yml` (dazu kommt `gam-engineering/ci/gitlab-docs.yml`). Ein GitHub-Workflow existiert nicht, GitHub ist nur ein Mirror.

## Wann sie läuft

In `.gitlab-ci.yml:4-11` ist festgelegt, dass pro Änderung genau eine Pipeline läuft:
- Ist ein MR offen, läuft eine **MR-Pipeline** (`merge_request_event`). Die zusätzliche Branch-Pipeline wird dann unterdrückt.
- Ohne offenen MR läuft bei jedem Push eine **Branch-Pipeline**.
- Bei einem **Tag** laufen die Checks noch einmal, danach wird ein Release veröffentlicht.

Für alle Jobs gilt: maximal **10 Minuten** Laufzeit (`timeout: 10m`), und ein neuer Push bricht den alten Lauf ab (`interruptible`).

## Stage `test`: alle Jobs laufen parallel

**Code-Qualität** (Image `node:24.14.0-alpine`, vorher `pnpm install --frozen-lockfile`, pnpm-Store und Turbo-Cache werden gecacht):

| Job | Was er macht |
|---|---|
| `lint` | `pnpm run lint` (über Turborepo) und `biome ci .` für die Root-Dateien |
| `typecheck` | `pnpm run typecheck` |
| `test` | `pnpm test` mit einem **Postgres-18-Service**, damit die DB-Tests (`TEST_DATABASE_URL`) eigene Datenbanken anlegen können |
| `build` | `pnpm run build` |
| `accessibility` | Baut `@stash/web` im Playwright-Image, startet `next start` und prüft mit **axe**. Der Job schlägt bei kritischen Verstößen fehl und kontrolliert außerdem, dass die Node-Major-Version zu `.tool-versions` passt |
| `commit-messages` | Prüft mit **commitlint** alle Commits seit der Merge-Base |

**Security** (entspricht `docs/security_next_js.md`, mit denselben Configs wie der lokale pre-commit):

| Job | Was er macht |
|---|---|
| `dependency-audit` | `pnpm audit --prod --audit-level=high` |
| `secret-scan` | **Gitleaks** über die Git-History, Config in `.gitleaks.toml` |
| `code-scan` | **Semgrep** mit den Regelsets javascript, typescript, react, nodejs, owasp-top-ten und `.semgrep.yml`. Schon ein einziger Fund lässt den Job fehlschlagen |
| `container-scan` | Baut mit Docker-in-Docker alle Images aus `docker-compose.yml` (alle Profile) und scannt jedes mit **Trivy** auf HIGH/CRITICAL-Lücken, für die es einen Fix gibt. Akzeptierte Ausnahmen stehen in `.trivyignore` und `.trivyignore.d/<service>` |

**Doku** (`docs`, nur bei MRs sowie auf `dev` und `main`):
- `markdownlint-cli2` über `gam-ai-knowledge/**/*.md`
- `doc-check.mjs --status` prüft, ob Roadmap und Status-Einträge zu den Merges und Tags im Git passen. Dabei wird der MR so behandelt, als wäre er schon gemerged.

## Stage `release`: nur bei Tags

1. `release-notes`: Der Tag muss SemVer sein (`v1.0.0`), und `CHANGELOG.md` muss einen Abschnitt dafür haben, aus dem `scripts/changelog.ts` die Notes erzeugt.
2. `release`: legt das GitLab-Release mit diesen Notes an.

## Zusammenhang mit dem Merge

Ein MR darf nur mit **grüner Pipeline** gemerged werden (P-MR-3). Schlägt irgendein Job fehl, ist der Merge blockiert. Dieselben Scanner (Gitleaks, Semgrep, pnpm audit, commitlint) laufen schon lokal über `.pre-commit-config.yaml`. Die Pipeline prüft sie also ein zweites Mal, falls jemand den Hook umgangen hat.
```
