# Release

Loaded by `/gam-engineering release [<version>]` (skill `gam-delivery`; P-VER-1…4). Without git there is no release: say so and stop (P-GIT-7). In branch model `trunk`, steps 2–6 run on `main` without a release MR, and the release key governs the tag ([references/branches.md](../../gam-engineering/references/branches.md)).

1. Determine the version from `VERSIONING.md`, P-VER-2, and the stories merged since the last tag. Under release `ask` (P-MR-5), confirm it as a `Q<n>`; under release `auto`, use it without asking and write the reasoning into the release notes — except a MAJOR bump, which is always confirmed as a `Q<n>`.
2. Set the version file (P-VER-4): write `<version>` into every version file of the project that already carries a version field — `version` in `package.json` (with its `package-lock.json`, e.g. `npm version <version> --no-git-tag-version`), `pyproject.toml`, `Cargo.toml`, `composer.json`, `<Version>` in a `*.csproj`, in the root and in the package folders of a monorepo — and commit them as `release: v<version>` on the integration branch (`dev`; trunk: `main`), so the tag of step 6 points at a commit that carries the released version. A file without a version field gets none; a project without a version file skips this step.
3. Call the Skill tool with `gam-v-pre-release-review` for `v<last tag>..dev` under override 9 of [gam-delivery](../SKILL.md#overrides-for-the-delivery-skills): migrations, configuration, secrets, rollout order, rollback risk. A blocker stops the release and is reported; a confirmation item becomes a `Q<n>`; the remaining risks go into the release notes.
4. Open the release MR `dev` → `main` with release notes that list the closed stories with IDs and titles (P-HUM-4).
5. Check that the pipeline on `dev` is green at every recorded location, as [merge](merge.md) step 1 checks it — at the release every recorded location is due, whatever `localWhen` and `ci.trigger` say (P-PIPE-8) —, but with the local runner called as `local-pipeline.ps1 -Tier release` so the slow checks (end-to-end tests, Trivy scans, SonarQube) run too (PP-F-27), and every story since the last tag met the Definition of Done; otherwise report and stop. Then merge per the effective release key (P-MR-5).
6. Create the annotated tag `v<version>` on `main` and publish the release on the git host (GitLab or GitHub Release) with the notes.
7. Status: ROADMAP stage `released` for every included feature, `shipped: "v<version>"` in the `epic.md` of every epic the release completes (a story of an epic shipped earlier gets its own `shipped`, P-DOC-6), position rows closed, log entry; `node gam-ai-knowledge/tools/doc-check.mjs --status` must report no `STATUS` error.
