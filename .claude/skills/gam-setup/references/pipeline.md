# Pipeline procedure

Loaded by `/gam-engineering pipeline` (skill `gam-setup`). It decides where the project's pipeline runs — `host` (CI on the git host), `local` (a script on the developer's computer), `both`, or `none` (no pipeline) — and records the decision in `gam-engineering/pipeline.json` (P-PIPE-1). The Definition of Done then names that file, so "green pipeline" names a pipeline the project can actually run (P-PIPE-2).

This version of the procedure decides the location and the checks, copies the local pipeline, and writes the host CI file: it detects the project's languages, proposes, from the check catalog, a dependency audit, a secret scan, the docs check, and per language static analysis, lint, and tests, copies the script that runs them on the developer's computer, and, when the pipeline runs on the host, generates the GitLab or GitHub CI file that runs them on every merge request (on GitHub: pull request). The developer may also choose `none`: the project then records that it has no pipeline, and nothing is copied or generated (PP-F-20). Setup runs this procedure for every new project, and `migrate tools` offers it to every project without a decision (PP-F-16). Run again, it starts from the recorded decision: it never loosens it without naming the loosening (step 8, PP-F-19) and never overwrites a generated file the team edited ([Own changes kept](#own-changes-kept), PP-F-18).

**A project with its own pipeline** — local pipeline scripts, a CI file or workflows that gam-engineering did not generate, or a note in `WORKFLOW.md` that the project keeps its own pipeline — is kept and completed, never replaced or changed without asking (P-PIPE-5): run [Merge with an existing pipeline](#merge-with-an-existing-pipeline) before step 5. By default `pipeline.json` records the gam checks the project's pipeline lacks, and both run.

The host is the one in `WORKFLOW.md`, *Git host / tracker*. In a folder without git, or with the tracker as local markdown, there is no host to ask: skip step 2, pass `{ "host": "" }` in step 3, and continue — the recommendation is then `local` with the runner state unknown.

## Steps

1. **Copy the helper.** Copy [templates/gam-engineering/tools/pipeline.mjs](../../gam-engineering/templates/gam-engineering/tools/pipeline.mjs) and [pipeline-catalog.json](../../gam-engineering/templates/gam-engineering/tools/pipeline-catalog.json) to `gam-engineering/tools/` when they are missing or differ from the templates. Copy `pipeline-merge.mjs` with them when the project has its own pipeline. Also copy the scripts of the recorded checks: `architecture-check.mjs` (checks `architecture` and `limits`), `floor-guard.mjs` (check `guard`), `sonar-check.mjs` (check `quality`), `ts-check.mjs` (the TypeScript checks), `integration-check.mjs` (check `integration`), and `committed-copy.mjs` (a check with `lintOnCommitted`), each from the same folder and each only when the decision records a check that runs it.
2. **Read the runner state** with the developer's existing CLI login; never ask for or store a token:
   - GitLab: `glab api "projects/:fullpath"` and `glab api "projects/:id/runners?status=online&per_page=100"`.
   - GitHub: `gh api "repos/{owner}/{repo}/actions/permissions"`.

   Each answer that exits non-zero or does not come within 30 seconds is `null` — the host did not answer or denied access.
3. **Get the recommendation.** Write the answers as one JSON object to a temporary file outside the repo — `{ "host": "gitlab", "project": <answer>, "runners": <answer> }` or `{ "host": "github", "permissions": <answer> }` — and run `node gam-engineering/tools/pipeline.mjs recommend <file>`. It prints `{ "location": …, "reason": … }`: `both` when a runner is usable, `local` when none is or when the runner state is unknown.
4. **Detect the languages and markers:** `node gam-engineering/tools/pipeline.mjs detect` in the repo root prints `{ "languages", "integration", "stackLint", "images" }` (PP-F-31). It searches the root and the subfolders down to the catalog's `detection.depth`, skipping dependency, build, and VCS folders. It prints each language whose manifest file it finds (`package.json` → Node, `composer.json` → PHP, …) with the folder as `cwd` (`""` for the root), so a monorepo yields one entry per part. It also prints the folders with integration or operations tests (for example `*.bats` files or an `ops/tests` folder), the folders with operations configuration (for example Compose, Kubernetes, proxy, or Terraform files), and one image per Dockerfile. Every list may be empty. The marker lists are data in the catalog, not assumptions of this procedure.
5. **Ask for the location and the languages** in one pop-up, one round ([Asking the developer](../../gam-engineering/SKILL.md#asking-the-developer)):
   - **Location**, one `Q<n>`: the options are `both`, `local`, `host`, and `none`; the recommended one comes first, and its description is the `reason` line exactly as printed. `none` comes last, is never recommended, and reads "no pipeline: no checks, no local script, no CI file" (PP-F-20). The pop-up asks even when the runner state is unknown.
   - **Languages**, multi-select: the detected languages first, each with its folder (`PHP · backend`) and marked as recommended, then the other catalog languages without a folder, in catalog order. A pop-up question holds at most four options and has no preselection, so the languages fill as many questions as needed. No answer in any question means no language.
6. **Propose the checks.** At location `none`, skip this step and step 7: the decision records no languages and no checks. Otherwise write `{ "languages": [<confirmed languages, as { "name", "cwd" } from step 4>], "markers": { "integration": [<folders>], "stackLint": [<folders>] }, "host": "<gitlab or github; empty without a host>", "hostTier": "<Host tier from WORKFLOW.md: Free, Premium, Ultimate, Team, or Enterprise; unknown when the tier check was inconclusive>" }` to a temporary file outside the repo and run `node gam-engineering/tools/pipeline.mjs propose <file>`. It prints the options in order — dependency audit, secret scan, docs, size limits, quality, then `integration` and `stack-lint` once per marker folder (only when step 4 found one), then static analysis, the architecture check (Node), the per-folder checks, lint, and tests per language and folder, then the host-native scanners the tier allows — each with its `check` (with `cwd` outside the root) and whether it is `recommended`. Of two overlapping catalog checks only one is recommended (`yieldsTo` in the catalog, Q279): the trivy audit yields to a language's own audit, `config` to `stack-lint`, `quality` to `sast`.
7. **Ask for the checks** in one pop-up, one round, keeping the printed order; the round is complete when every printed option sits in exactly one question:
   - One multi-select question per kind: the checks without a language (audit, secrets, docs, limits, guard, quality), `integration` and `stack-lint` (only when offered), `sast`, `architecture`, `lint`, `tests`. A kind without options gets no question.
   - Fit the limits: a kind with only one option joins the question before it; a question with more than four options is split into two of nearly equal size. A round with more than four questions is sent as several calls in a row.
   - Each label names the check, its language, and its tool, the audit also its threshold (`audit · trivy · high`, `lint Node · npm run lint`, `sast Node · gitlab-sast (native)`). Options with `recommended` true are marked as recommended; native scanners never are (PP-F-7).
   - The free-text answer may replace a proposed lint or test command with the project's own (`lint Node: npm run check`); that command line becomes the check's `tool`. A chosen `integration` or `stack-lint` check has no command yet: ask for it in the same round, one `Q<n>` per check, with the commands the project already uses as options; never invent one. It may also set a check's threshold to another level of the catalog's `thresholds` (`audit · trivy · critical`); that level becomes the check's `threshold`.
   - When `gam-engineering/pipeline.json` exists, its recorded checks are the recommended options instead, each labelled with its recorded tool and threshold, so accepting the recommendations keeps the decision as it is.
8. **Name a loosening, then write the decision.** When `gam-engineering/pipeline.json` exists, compare before anything is written: write `{ "previous": <the recorded decision>, "next": <the new one> }` to a temporary file outside the repo and run `node gam-engineering/tools/pipeline.mjs compare <file>`. It prints every loosening — a threshold that blocks fewer findings, a removed check, a dropped `lintOnCommitted`, a dropped location, a changed `ci.trigger` (PP-F-36) — as `{ "change", "noLongerRed" }`, or `[]`. When it prints any, ask one confirmation `Q<n>` that calls the change a loosening and lists each `change` with its `noLongerRed` ("audit threshold high → critical — high findings will no longer turn the pipeline red"); options **Keep the decision** (recommended) and **Loosen**. On *Keep the decision* (or no answer) only the round is logged; nothing else is written and the procedure ends here. Otherwise write the decision to `gam-engineering/pipeline.json`. `checks` holds the `check` of every chosen option, in the printed order, exactly as `propose` printed it — with its `tool` and, for the audit, its `threshold`:

   ```json
   {
     "version": 1,
     "location": "<the answer: host, local, both, or none>",
     "languages": ["<the confirmed languages, in catalog order>"],
     "hostTier": "<as passed to propose>",
     "checks": [
       { "kind": "audit", "language": "", "tool": "trivy", "threshold": "high", "native": false },
       { "kind": "docs", "language": "", "tool": "doc-check", "threshold": "", "native": false }
     ],
     "ci": "",
     "localScript": "gam-engineering/local-pipeline.ps1",
     "decidedOn": "<today, YYYY-MM-DD>"
   }
   ```

   `localScript` is `gam-engineering/local-pipeline.ps1`, the script step 9 copies, and `""` at `none`; `ci` is set by step 10. A check may carry the optional fields of [Folders, triggers, and the new checks](#folders-triggers-and-the-new-checks): `cwd`, `lintOnCommitted`, `version`, `services`, `ciImage`; the decision may carry `images`. At `none`, `languages` and `checks` are `[]`. If the file exists, keep `ci` and replace the other fields.
9. **Copy the local pipeline.** At location `none`, copy nothing: remove a `gam-engineering/local-pipeline.ps1` left from an earlier decision (a copy the team edited only when the developer names it, [Own changes kept](#own-changes-kept)), then run the `validate` at the end of this step. Otherwise copy [templates/gam-engineering/local-pipeline.ps1](../../gam-engineering/templates/gam-engineering/local-pipeline.ps1) to `gam-engineering/local-pipeline.ps1` when it is missing. When it exists and differs from the template, follow [Own changes kept](#own-changes-kept). Add the line `gam-engineering/reports/` to `.gitignore` (create the file if it is missing) unless a line already ignores that folder: every run writes its report to `gam-engineering/reports/local-pipeline/<yyyy-MM-dd-HHmmss>/report.md`, which stays out of git. When `secrets` is recorded, copy [templates/gitleaks.toml](../../gam-engineering/templates/gitleaks.toml) to `.gitleaks.toml` in the repo root when it is missing; when it exists, keep it and add only the allowlist paths of the template it lacks (PP-F-45). gitleaks reads that file in both scans, so the git-ignored `.env.sonar` and `.scannerwork/` of the `quality` check never turn `secrets` red; those two files must stay git-ignored, because the allowlist also hides them from the history scan. Paths of the project's own, such as invented test fixtures, are the project's to add there. Then run `node gam-engineering/tools/pipeline.mjs validate gam-engineering/pipeline.json`; it must print `[]`.
10. **Write the host CI file.** It is `gam-engineering/ci/gitlab-pipeline.yml` on GitLab and `.github/workflows/gam-engineering-pipeline.yml` on GitHub:
    - **Location `host` or `both`:** run `node gam-engineering/tools/pipeline.mjs render-ci <gitlab or github> <integration branch>` — the integration branch is `main` in branch model `trunk`, else `dev` (P-GIT-9). It prints `{ "path", "includeIn", "content" }` with one job per recorded check and the docs job (a Node job installs by the lock file in its folder: `npm ci`, `pnpm install --frozen-lockfile`, or `yarn install --immutable` through corepack, none without a lock file, PP-F-55), running on the events of `ci.trigger`, then one build job per recorded image ([Folders, triggers, and the new checks](#folders-triggers-and-the-new-checks)). When the host's CI file is missing or equal to that content, add `--write` to write it; when it exists and differs, follow [Own changes kept](#own-changes-kept). An exit code 1 names a check the catalog cannot render: stop and show the message. Set `ci` to that path in `pipeline.json`, or to `{ "file": <path>, "trigger": <trigger> }` when the trigger is not `merge-request`. On GitHub the workflow needs no include; name its jobs (`gam-audit`, `gam-docs`, …) to the developer as the status checks to require in the protection of the integration branch, as the docs check was (P-MR-3). On GitLab, make `.gitlab-ci.yml` include it (`include:` with `- local: gam-engineering/ci/gitlab-pipeline.yml`; create the file if it is missing, add the entry to an existing `include` otherwise, turning a single string or map into a list that keeps it).
    - **Every location:** remove the separate docs CI file — on GitLab `gam-engineering/ci/gitlab-docs.yml` (or its old path `.gitlab/ci/docs.yml`) with its entry in the `include` of `.gitlab-ci.yml`, on GitHub `.github/workflows/gam-engineering-docs.yml` (or its old path `.github/workflows/docs.yml`); the docs job now runs in the generated file or in the local pipeline, and at `none` only where an agent runs doc-check. At location `local` or `none`, `ci` is `""`, and a generated host CI file left from an earlier `host` or `both` is removed, on GitLab with its `include` entry, so a dropped host pipeline no longer runs; a copy the team edited is removed only when the developer names it ([Own changes kept](#own-changes-kept)).
    - **Lint it** (location `host` or `both`) before the change goes to its MR. On GitHub: `actionlint .github/workflows/gam-engineering-pipeline.yml`, which runs offline. On GitLab: `glab ci lint gam-engineering/ci/gitlab-pipeline.yml` — the generated file itself, not `.gitlab-ci.yml`: GitLab resolves a local include against the default branch, where the new file does not exist yet. When the linter rejects the file or is missing, open no MR: show the linter output and stop (PP-E-5). Then run `node gam-engineering/tools/pipeline.mjs validate gam-engineering/pipeline.json` again; it must print `[]`.
11. **Point the Definition of Done at the decision.** Item 2 of the Definition of Done in `gam-ai-knowledge/WORKFLOW.md` reads as in [templates/WORKFLOW.md](../../gam-ai-knowledge/templates/WORKFLOW.md): it names `gam-engineering/pipeline.json` and never copies the location into `WORKFLOW.md`.
12. **Ship it** like every change (P-GIT-2): the decision (its question rounds are in the chat export), the helper with its catalog, the local pipeline, `.gitignore`, `.gitleaks.toml` (when `secrets` is recorded), the generated CI file (on GitLab with `.gitlab-ci.yml`) and the removed docs CI file, and `WORKFLOW.md` in one commit on a work branch. The MR description names the linter result of step 10 (`glab ci lint`: valid; `actionlint`: no findings); a project that merges without MRs names it in the commit message and the log entry.

## Merge with an existing pipeline

For a project with its own pipeline (P-PIPE-5, PP-F-37, PP-F-38). Nothing is created before point 1 is done.

1. **Show the earlier decision first.** Read `WORKFLOW.md` and the project's ADRs for a decision about the pipeline: a note that the project keeps its own pipeline, a `Q<n>` against a `pipeline.json`, an ADR that allows CI only for releases. Name each to the developer, with its ID, before anything is written. Such a decision is continued with the result of point 5, never overwritten.
2. **Inventory.** `node gam-engineering/tools/pipeline.mjs inventory` prints the jobs of the project's CI files (GitLab `.gitlab-ci.yml` with its local includes, GitHub workflows; the gam files are left out) as rows `{ "job", "source", "checks", "trigger", "command", "suggested": { "kind", "language", "cwd" } }`. Read the project's local pipeline scripts yourself and add one row of the same form per job they run. Show the inventory as a table *Job — what it checks — trigger — command*.
3. **Map each row to a check kind** of the catalog (`lint`, `tests`, `format`, `types`, `quality`, `integration`, `stack-lint`, `audit`, …). Give it the project's command as `tool` and its folder as `cwd`. Add what the job does beyond the command: `lintOnCommitted` for a lint on the committed state, `services` for a throwaway dependency, `version` for a scan with the release version. Write the result into the row as `check`. A row without a catalog kind becomes a check of kind `custom` with the project's command, so no job is lost; an image build becomes an entry of `images`.
4. **Unite.** Run steps 4 and 6 for the gam options. Then write `{ "rows": [<rows>], "proposed": [<the recommended options>] }` to a temporary file outside the repo and run `node gam-engineering/tools/pipeline.mjs merge <file>`. It prints `union`, `gamOnly`, `projectOnly`, and `duplicates`:
   - The same job in the project's CI file and in its local script counts once: the more precise one stays (*duplicate in the project*).
   - Two checks of the same kind, language, and folder are a duplicate. Two checks that run the same tool (the catalog's `detection.overlapTools`) in the same folder overlap and count as a duplicate too (Q278).
   - Of each pair the more precisely configured check wins — its own command, a folder, `lintOnCommitted`, settings — and on a tie the project's. The other is dropped.
   - Each pair is one line *duplicate: X and gam Y, X wins, because …*.
5. **Confirm in one round**, one `Q<n>` with the duplicate lines in the question. The options are **gam checks only** (recommended: `pipeline.json` records the gam checks the project lacks, the `gamOnly` list; the project's local pipeline and CI file stay as they are and run too), **Union** (`pipeline.json` describes every project job and the gam checks; the project's own pipeline is replaced only through point 6), **Project pipeline only** (`pipeline.json` describes the project's jobs and nothing else), and **Change nothing**. The chosen list is the decision's `checks` in step 8. Record the result next to the earlier decision of point 1 in `WORKFLOW.md` (`merged into gam-engineering/pipeline.json on <date>, Q<n>`).
6. **Replacing the project's pipeline — only after *Union* and its own `Q<n>`** (P-PIPE-5). The project's local pipeline and CI file are never changed without the developer agreeing in a pop-up. Under *gam checks only* both pipelines are the gate and `WORKFLOW.md` names both. Under *Union*, the project's pipeline stays the one `WORKFLOW.md` names until the switch, and the switch is its own change:
   - Run the merged pipeline once as a probe (`local-pipeline.ps1 -Tier release`) and compare it job by job with the inventory.
   - When every old job is covered and the probe finds as much or more, the switch change makes `pipeline.json` and `local-pipeline.ps1` the pipeline. It removes the old local scripts and the old CI jobs the generated file now covers (an edited file only when the developer names it, [Own changes kept](#own-changes-kept)), and points `WORKFLOW.md` at the decision.
   - A gap the probe finds is fixed in the decision first.
7. **A project ADR governs the trigger.** An ADR that allows CI only for releases sets `ci.trigger` to `release-only`; no generated job may run on an event the ADR excludes. Ask for the trigger only when no ADR decides it.

## Folders, triggers, and the new checks

The fields a recorded check or the decision may carry beyond kind, language, tool, threshold, and native (PP-F-32 … PP-F-41). Every command comes from the project; the examples are only examples. A recorded command line is split at spaces and run without a shell, locally as on the host: a job that needs quotes, pipes, `&&`, or shell variables goes into a script of the project, recorded as its call (for example `bash scripts/ci/backend-lint.sh`).

- **`cwd`** — the folder of the check, relative to the repo root (`backend`, `apps/web`); empty or missing is the root. A project command runs in that folder, locally and on the host; a catalog script is told the folder through `--cwd=<folder>` (`ts-check.mjs` looks for its configuration there). The CI job of a check with `cwd` runs its setup and script lines in that folder. Two checks of the same kind and language differ by `cwd`; the job name carries the folder (`gam-lint-php-backend`).
- **`integration`** — tests against a throwaway environment. The check records the project's command as `tool`, its `cwd`, and `services`, each `{ "name", "image", "port", "env" }` (for example a database). `integration-check.mjs` creates its own network and starts each service with `--rm`. It waits until the service's port answers (`readySeconds`, default 60) and runs the command with `GAM_NETWORK` and `GAM_SERVICE_<NAME>_HOST`, `_PORT`, and `_ALIAS`. It removes the containers and the network whatever the result (P-PIPE-4). Without a container runtime the state is `not run`, not red. It runs locally only.
- **`stack-lint`** — the operations configuration (Compose, Kubernetes, proxy, Terraform files), with the project's command as `tool`, like lint and tests.
- **`custom`** — a job of the project's own pipeline with no catalog kind, kept with its command (point 3 of the merge).
- **`after`** — a list of check kinds this check waits for in a parallel run (for example a scan with its own script after `tests`, whose coverage it reads).
- **`tier`** — `merge` or `release` on any check, in place of the catalog's tier: a slow project job (for example a scan with its own script) runs only in the release run (PP-F-42).
- **`ciImage`** — the container image in which a `stack-lint` or `custom` check runs on the host; without it the check runs locally only.
- **`lintOnCommitted`** — on a `lint` or `format` check: the check runs through `committed-copy.mjs` in a temporary copy of `git archive HEAD` with LF line endings, as the git host sees it. The working tree's git-ignored folders (installed dependencies) are linked in, and the copy is deleted afterwards. Line-ending settings such as `core.autocrlf=true` otherwise hide real lint findings on Windows.
- **`version`** — on the `quality` check: the version SonarQube records. Empty is the next MINOR after the newest tag `v<major>.<minor>.<patch>`, because SonarQube counts everything since the previous version as new code. `-Skip quality` still leaves the scan out.
- **`images`** — `[{ "name", "dockerfile", "context" }]`, from the Dockerfiles step 4 found; when the location is `host` or `both`, ask which to record (multi-select, all recommended). `render-ci` adds one build job per image. It runs after every check job, on pushes only, and pushes to the host's registry (GitLab `$CI_REGISTRY_IMAGE/<name>`, GitHub `ghcr.io/<repository>/<name>`), tagged with the commit and, on a release tag, with the tag.
- **`ci.trigger`** — recorded as `"ci": { "file", "trigger" }`; a plain path means `merge-request`.
  - `merge-request` (default): checks on every merge request and the integration branch, with images also on release tags; builds on the integration branch and tags.
  - `release-only`: checks on merge requests into `main`, on `main`, and on tags; builds on `main` and tags.
  - `both`: the union of the two.

## Local containers

When a check needs a local container — a SonarQube server, a Semgrep scan — start it without a pop-up and stop the containers you started once the run ends, as P-PIPE-4 sets out.

## Docs-only run

P-PIPE-6, PP-F-49. Under flow `full` the local runner at tier `merge` runs only `docs`, `secrets`, and `audit` when every changed file is a document; the other recorded checks show as `skipped by choice` with the reason `only documents changed (P-PIPE-6)`, and the report names them. The choice is the field `docsOnly` of `gam-engineering/pipeline.json`: `slim` (default, no entry needed) or `full`; set `full` only on the developer's request. The lists that decide what a document is (`documentPaths`, `stackFiles`, `dataFolders`) are the `docsOnly` block of the check catalog, never edited per project; a project that keeps test data or fixtures in an unlisted folder sets `docsOnly` to `full`. A doubtful file, git unable to answer, and `-Tier release` give the full run. The host CI file is unchanged.

markdownlint is no pipeline check (Q295): the `docs` check is doc-check only. Run `npx --yes markdownlint-cli2 "**/*.md"` when the developer or a command asks for it.

## Flow quick

Under `env.GAM_ENGINEERING_FLOW` = `quick` ([Quick mode](../../gam-engineering/references/quick.md), P-PIPE-3) the location is `local` and no runner state is read: skip steps 2, 3, 6, and 7. Ask the languages of step 5 only to record them. Ask one `Q<n>` for the short test: one command line that takes seconds (a smoke test of the scripts, `npm test`), or *none* if the project has no code. Record it as a check, `{ "kind": "tests", "language": "", "tool": "<the command line>", "threshold": "", "native": false }`. Ask a second `Q<n>`, multi-select, for the architecture checks of [Architecture checks](#architecture-checks): `limits` always, `architecture` when the languages include Node, and `guard` of [Weakening guard](#weakening-guard), all recommended; record each chosen one as its `propose` option says (run `propose` with the confirmed languages and take the options of kind `limits`, `architecture`, and `guard`). With *none* and no architecture check record `checks: []`. Steps 8–9 and 11–12 apply as written; step 10 writes no host CI file. The local pipeline then runs nothing when no code file changed (a change of `pipeline.json` counts as a code change) and only this test, the architecture checks, and the weakening guard when one did (P-PIPE-3). A later switch to `full` runs `/gam-engineering pipeline` again.

## Architecture checks

Two catalog checks enforce P-ARCH, both run by `gam-engineering/tools/architecture-check.mjs` and both also run under flow `quick` when code changed (P-PIPE-3).

- **`limits`** (no language, recommended): fails a code file over `maxFileLines` (default 400) or a function over `maxFunctionLines` (default 60). To change a limit or skip a path, edit the recorded check in `gam-engineering/pipeline.json`: `{ "kind": "limits", …, "settings": { "maxFileLines": 500 }, "exclude": ["src/generated"] }`; loosening it is a loosening of the decision (step 8). The check reads every code file, not only the changed ones, except the skills' own copies in `gam-engineering/` and `gam-ai-knowledge/`: when it is first recorded in a project with older oversized files, run it once and offer those files as `exclude` entries, so the next change is not red for code it did not touch.
- **`architecture`** (Node, recommended): dependency-cruiser through `npx`; the cycle rule always, and the rule that a layer imports only from layers inside it (P-ARCH-1), generated from the table under *Layering chain* in `STACK.md` §4 (P-DES-3). Without that table only the cycle rule runs and the check prints that the chain is missing; when the check is offered, name the missing chain to the developer and point to `STACK.md` §4.
- **No `any`** is no catalog check: where the project uses Biome, `migrate tools` sets `noExplicitAny` to `error` in the Biome config (P-ARCH-3, P-DES-10).

## Weakening guard

The catalog check `guard` (no language, recommended, P-PIPE-7) runs `gam-engineering/tools/floor-guard.mjs check` and also runs under flow `quick` when code changed, but not in the docs-only run. It reads the diff against the merge base with the integration branch and fails on a new suppression comment, an added skip or only, a deleted test file, fewer assertions in a kept test file, and a loosened value or removed check in `pipeline.json`. A hit passes only with a line `- <path>: <move> - <reason>` (moves `suppression`, `skip`, `deleted-test`, `fewer-assertions`, `loosened`) that the same change adds to `gam-engineering/guard-reasons.md`; the change that needs a reason creates the file and starts it with a heading line (markdownlint MD041). The generated CI jobs install git, fetch the full history and the target branch, and pass it as `GAM_GUARD_BASE`. When the check is first recorded, run it once: a run without a merge base is `not run` (exit 2), and the agent names the cause instead of recording the check as green.

## TypeScript checks and tiers

A project with a `tsconfig.json` gets the language `TypeScript` in step 5 and these checks (PP-F-29, PP-F-30), all run by `gam-engineering/tools/ts-check.mjs`.

- **Tier `merge`** (every merge): `format` (Biome), `types` (`tsc --noEmit`), `tests` (Vitest with coverage; thresholds 80 % lines and statements, 75 % branches), `audit` (`pnpm audit` for `pnpm-lock.yaml`, `npm audit` for `package-lock.json`). Under flow `quick` `format`, `types`, and `tests` also run (P-PIPE-3).
- **Tier `release`** (only `local-pipeline.ps1 -Tier release`, which the `release` command calls, PP-F-27): `e2e` (Playwright), `image` and `config` (Trivy, local binary), and `quality` (SonarQube). They have no CI job. `image` builds a throwaway image from the `Dockerfile` and removes it afterwards.
- **Missing configuration:** a check whose file is missing exits with 3 and the report shows `not run`. Offer to create the file when the check is chosen: `biome.json` (with `noExplicitAny` as `error`, P-ARCH-3), a `vitest.config.ts` with the thresholds above, a `playwright.config.ts`. A lock file is created by the package manager, never by this procedure.
- **Parallel run:** the runner runs up to `-Jobs` checks at the same time (default `GAM_PIPELINE_JOBS`, else the number of processors, at most 4; `-Jobs 1` one after the other), each in its own PowerShell process (PP-F-43). A console shows one live table — check, state, seconds — that updates in place; without a console (an agent run) one line per change. A check waits for the checks of the kinds in its `after` (the catalog's `quality` waits for `tests`, whose coverage it reads; a recorded check may name its own). The `sast` checks of several languages run as one semgrep call with every rule set.
- **Report:** every run writes its own folder `gam-engineering/reports/local-pipeline/<yyyy-MM-dd-HHmmss>/` with `report.md` and one `<kind>-<tool>.md` per check; `report.md` keeps the decision's order whatever finished first and names the seconds of each check; the last 10 folders stay (PP-F-28). The folder exists from the start: while the run lasts, `report.md` ends with the line `running` and shows each check as `waiting`, `running since <HH:mm:ss>`, or its result, each output file appears as soon as its check ends, and a running check of a parallel run writes its output live to `<name>.running.txt`. The runner sets no time limit; a check that hangs is seen there and stopped by hand (PP-F-46).
- **Tool versions:** locally the runner calls the tool found on the search path, whatever its version; the catalog's `version` pins the container images (semgrep, the CI jobs) and names the version of the install hint. A newer local tool, such as gitleaks 8.30 against the pinned 8.21.2, may find more than the CI job.
- **Git worktrees:** a container check (semgrep) mounts only the worktree folder, whose `.git` file points outside it, so the tool cannot ask git which files are ignored and reads them all; run the pipeline in a normal checkout.

## SonarQube check

The catalog check `quality` (no language, local only, tier `release`, recommended) runs `gam-engineering/tools/sonar-check.mjs scan` (PP-F-24), which calls the skill `gam-sonar`'s `scripts/scan.ps1` (scanner image, network `sonarqube-shared`, quality gate awaited; the version is pinned in gam-sonar only, Q376) and then its `scripts/export-report.ps1` (Q377). A failed gate turns the pipeline red and the message points to the skill `gam-sonar` for the evaluation. The export reads the gate, the measures (with metric names, ratings as A–E, debt as days/hours/minutes, `%`), and the open issues from the REST API and writes `quality-sonarqube-<YYYY-MM-DD>_<HH-MM-SS>.md` into the run folder next to `report.md` (PP-F-52, PP-F-53), also when the gate failed, and keeps only the newest four such reports of that folder (PP-F-53). It runs only at tier `release` (`local-pipeline.ps1 -Tier release`, which the `release` command calls), never in the default merge tier or under flow `quick`, and has no CI job.

- The check needs the skill `gam-sonar` on every computer that runs it: that skill names the folder of the shared stack on this computer (its `compose.yaml` and `start.ps1`) and evaluates a failed gate. Without it, the agent offers `-Skip quality` instead of guessing a server.
- When the check is offered, create `sonar-project.properties` with the project key (the one `gam-sonar` uses) and add `.env.sonar` and `.scannerwork/` to `.gitignore` (P-TEAM-2). The agent creates the token file itself (Q288, Q289, 2026-10-29): when the stack's folder holds `new-token.ps1`, run `pwsh -File <stack folder>/new-token.ps1 -ProjectPath <repo root>`, which logs in with the admin password kept next to it, writes `.env.sonar`, and never prints the token or the password; without that script, the developer creates it with `gam-sonar`'s `generate-token.ps1`, which asks for the password. A scan that answers `401` needs a new token the same way. The report needs a second key `SONAR_USER_TOKEN` (a user token with the Browse right; the analysis token gets 404 on the gate and the measures) in the same file; the stack's `new-token.ps1` writes both keys since 2026-11-04 (`gam-sonar`); an older stack copy writes only `SONAR_TOKEN`, and the developer replaces it from `gam-sonar`'s `stack/sonarqube-shared/` before the release run. Without the key the check is red before the scan starts, and an API that does not answer for it is red too.
- Before a run, start the shared stack with its `start.ps1`, never a project's own SonarQube services, as P-PIPE-4 allows. Without the properties file, the token file, a container runtime, or a server that answers `UP`, the scan exits with 3 and the report shows `not run`, which turns the pipeline neither red nor green (PP-F-25).
- `local-pipeline.ps1 -Skip quality` leaves a kind out and the report shows `skipped by choice` (PP-F-26).
- The check `sonar-summary` (no language, local only, tier `release`, offered with `quality`, runs after it, PP-F-54) runs `gam-engineering/tools/sonar-summary.mjs`: it reads the newest `quality-sonarqube-<YYYY-MM-DD>_<HH-MM-SS>.md` of the run folder and prints the path, the quality gate, the issues per severity, and always the HIGH-risk issues (BLOCKER, HIGH, CRITICAL). A gate `ERROR` turns the pipeline red; no report or no gate line exits with 3 (`not run`). `-Skip sonar-summary` leaves it out.

## Own changes kept

The generated files — `gam-engineering/local-pipeline.ps1` and the CI file of step 10 — may carry the team's own edits (PP-F-18). Whenever this procedure or `migrate tools` would write one that exists and differs from what it would write (the template, or a fresh `render-ci`), it shows the diff and writes the file only when the developer names it in a `Q<n>`; otherwise the file stays as it is. For the local pipeline, run `node gam-engineering/tools/pipeline.mjs runner-gaps` before that question: it prints, per feature the kept copy lacks and the decision needs (`tier`, `not-run`, `skip`, `live-report`), the checks that rely on it and what the old runner does instead, such as running release-tier checks on every merge; the question names each gap, and with a gap, replacing the copy is the recommended option (PP-F-47). A file that only differs in line endings counts as equal. The helper and the catalog of step 1 are the skill's own and are replaced.
