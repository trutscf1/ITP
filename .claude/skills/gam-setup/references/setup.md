# New project setup

Loaded by `/gam-engineering setup` (skill `gam-setup`).

For a fresh repo that should follow the user's standard process:

0. **Ask the start basis.** Run [Start basis](start.md) steps 1–4 (P-GOAL-4): requirements document, existing project, or only an idea, and the summary of that basis. Its steps 5–7 (`START.md`, the adoption of a foreign project, the next step) run right after step 1, in the same change.
1. **Create the knowledge folder and define the project goal.** Run [gam-ai-knowledge: Init](../../gam-ai-knowledge/references/init.md) (P-DOC-11): it asks the goal first — derived from the summary of step 0, that is from the approved project application (*Projektantrag*, SMART goals) or the existing project if one exists: one goal of at most 200 characters, target users, 1–3 measurable success signals, non-goals — and creates `gam-ai-knowledge/` with every knowledge document, `MANIFEST.md`, `tools/doc-check.mjs`, and the `AGENTS.md` pointer. Nothing else is created before the goal exists (P-GOAL-1). If the skill `gam-ai-knowledge` is not installed, stop with "Setup needs the skill gam-ai-knowledge; install it and run the command again".
2. **Ask solo or team** (as a `Q<n>`, see [Asking the developer](../../gam-engineering/SKILL.md#asking-the-developer)), and with git in the same round the branch model (P-GIT-9: **trunk** recommended for solo, **dev** for team) and the flow (P-FLOW-1: **quick** or **full**, recommended by the code size as in [Quick mode](../../gam-engineering/references/quick.md#entry-question)), and set up accordingly ([manifest: Team Mode](../../gam-ai-knowledge/templates/concept_authoring_manifest.md#team-mode)). With git, ask in the same round the footprint once (QA0053, [Footprint](#footprint)): **tracked** (recommended), **minimal**; minimal is offered only in solo mode. In a folder without git, make the one offer of [Projects without git](../../gam-engineering/references/no-git.md) first; if it is declined, the mode is solo and is not asked, step 6 and the CI job of step 10 are skipped, and step 7 writes the settings template unchanged without its question.
3. Keep `gam-ai-knowledge/MANIFEST.md` as step 1 copied it from [templates/concept_authoring_manifest.md](../../gam-ai-knowledge/templates/concept_authoring_manifest.md).
4. Copy [templates/CLAUDE.md](../../gam-engineering/templates/CLAUDE.md) to the repo root and fill in the `[placeholders]`.
5. Configure the agent files the callable skills read — tracker commands and domain-doc layout in `gam-engineering/agents/` — per [references/setup-tracker.md](setup-tracker.md), and create the root `CONTEXT-MAP.md` from [templates/CONTEXT-MAP.md](../../gam-engineering/templates/CONTEXT-MAP.md) (P-DOC-2).
6. Set up the tracker per P-TRK-1. Ask for the host (GitLab or GitHub) as a `Q<n>`; on GitLab, run the tier check instead of asking for the tier (P-TRK-4), then copy [templates/gitlab/](../../gam-engineering/templates/gitlab/) to `.gitlab/` or [templates/github/](../../gam-engineering/templates/github/) to `.github/` (issue templates for epics, user stories, and bugs, MR or PR template), ask for the sprint mode (`dated` / `fixed` / `goal`, and the length for `fixed`, P-TRK-1) as one `Q<n>`, create the labels and the first sprint milestone in that mode's form (on GitHub also the Project board), protect `main` and `dev` (in branch model `trunk` only `main`, with the approvals in team mode), and allow only merge commits (no squash, no rebase). For merge policy `approved`, also require `GAM_ENGINEERING_APPROVALS` approvals on `dev`.
7. Ask for the merge policy (`ask` / `approved` / `auto`, P-MR-4), the approval count, and the release merge (`ask` / `auto`, P-MR-5) as one `Q<n>`, and in the same round whether commits and MRs credit the AI (P-GIT-8; options **No** (recommended) and **Yes**), then write `.claude/settings.json` from [templates/claude/settings.json](../../gam-engineering/templates/claude/settings.json) — the `attribution` key for *No* or no `attribution` key for *Yes*, the `model` key and the two model tiers with their template values (stated as an assumption, changed later with `settings model`), `plansDirectory` set to `./gam-ai-memory/plans` (P-DOC-7), the three merge `env` values, `GAM_ENGINEERING_BRANCHES` and `GAM_ENGINEERING_FLOW` from step 2, the merge guard only under `ask` (plus its trunk rules in branch model `trunk`, P-MR-6), `GAM_ENGINEERING_FOOTPRINT` = `minimal` when step 2 chose it (for `tracked` the key stays out, so a later `migrate stealth` reads as `stealth` through `GAM_STEALTH_TARGET`), `env.CLAUDE_CODE_SUBAGENT_MODEL` equal to the draft tier, `env.GAM_ENGINEERING_SKILL_TRIM` and `env.GAM_ENGINEERING_SKILLS_KEEP` (copy `skill-trim.mjs` and `compact-hint.mjs` too), the `Stop` and `SessionStart` hooks, and the `PostToolUse` hook with matcher `Read` — and copy [templates/gam-engineering/tools/status-reminder.mjs](../../gam-engineering/templates/gam-engineering/tools/status-reminder.mjs) to `gam-engineering/tools/`, where the `Stop` hook calls it, and [inbox-names.mjs](../../gam-engineering/templates/gam-engineering/tools/inbox-names.mjs), which the `Read` hook calls to name the entries of the inbox (P-ROAD-3); both run with Node on every platform. If the settings file exists, merge into it without dropping other settings. In the same round ask whether the limit guard is on (P-WS-12; **On** recommended, **Off**; the description says it needs a Pro, Max, or Ultra plan and hides a personal status line), and for on the stop action (`auto` recommended: run `stopp` at once; `ask`: pop-up first; `env.GAM_ENGINEERING_LIMIT_ACTION`): on copies `limit-statusline.mjs` and `limit-guard.mjs` and keeps the template's `statusLine`, guard hooks, and `env.GAM_ENGINEERING_LIMIT_*` keys; off writes `GAM_ENGINEERING_LIMIT_GUARD=off` and drops the `statusLine` and the guard hooks.
8. Fill the process documents step 1 created in `gam-ai-knowledge/`: [ROADMAP.md](../../gam-ai-knowledge/templates/ROADMAP.md) (add the planned features, if any), [ROADMAP-DETAILS.md](../../gam-ai-knowledge/templates/ROADMAP-DETAILS.md) (keep the solo or the team position section), [next.md](../../gam-ai-knowledge/templates/next.md) (solo; in team mode `team/<handle>/next.md` per developer instead), [WORKFLOW.md](../../gam-ai-knowledge/templates/WORKFLOW.md) (mode, host, labels, sprint mode, Definition of Done, release steps, time tracking on/off), [VERSIONING.md](../../gam-ai-knowledge/templates/VERSIONING.md), and the product backlog `work-items/BACKLOG.md` ([template](../../gam-ai-knowledge/templates/work-items/BACKLOG.md)), whose table stays empty (P-DOC-8).
9. Fill `gam-ai-knowledge/STACK.md` ([template](../../gam-ai-knowledge/templates/STACK.md)): §0, §1, and §8 now, the rest as the first concept reaches Phase 5. Fill in §10 now too, by step 2 of [Frontend](frontend.md). `CONTEXT.md`, `TEST_STRATEGY.md`, `DEPLOYMENT.md`, and `SECURITY.md` stay as step 1 created them until a concept or the architecture fills them.
10. Copy the documentation checks. Everything the skill copies into a project carries its name so it cannot collide with the project's own files: scripts and guides go to the folder `gam-engineering/` in the repo root, the CI job and the hook get the prefix `gam-engineering-`. The checker `gam-ai-knowledge/tools/doc-check.mjs` came with step 1; copy [templates/.markdownlint.jsonc](../../gam-engineering/templates/.markdownlint.jsonc) and [templates/.markdownlint-cli2.jsonc](../../gam-engineering/templates/.markdownlint-cli2.jsonc) to the repo root. Then run [Pipeline](pipeline.md), steps 1–11 (under flow `quick`: [the short test and the architecture checks](pipeline.md#flow-quick) instead of steps 2–7; the checks are described in [Architecture checks](pipeline.md#architecture-checks)), which decides where the pipeline runs and which checks it runs and writes the host CI file, which holds the docs job (P-PIPE-1); its rounds belong to this setup, and its files ship with the setup commit. If the repo publishes itself, add the P-DOC-9 entries to its publish lists as in the *Publish lists* row of [Migrating the tooling](migrate-tools.md), stated as an assumption `A<n>`. If the project formats with Biome (`biome.json` or `biome.jsonc`), set it up as the *Biome on write* row of the same file says (P-DES-10), stated as an assumption `A<n>`. Run `node gam-ai-knowledge/tools/doc-check.mjs` once; on the fresh documents it must exit with 0 and report no `PUBLISH-LEAK`. With git, also copy the manual merge kit: [templates/gam-engineering/tools/merge.mjs](../../gam-engineering/templates/gam-engineering/tools/merge.mjs) and [templates/gam-engineering/tools/MERGING.md](../../gam-engineering/templates/gam-engineering/tools/MERGING.md) to `gam-engineering/tools/` — the guide and script for merging into `dev` and releasing to `main` without an agent (*I merge myself*, P-MR-4). With git, run [Line endings](#line-endings) (P-GIT-12), stated as an assumption `A<n>`. With git, run [Worktree tooling](#worktree-tooling) (P-WS-13). Then run [AI chat export](#ai-chat-export), and write `gam-engineering/version.json` with the highest entry of [migrations.md](migrations.md) ([migrate.md: Step 5](migrate.md#step-5--version)).
11. **Create the short-term memory.** Run the setup part of [Memory check](memory.md#in-setup-and-migrate): with gam-ai-memory installed and current, `/gam-ai-memory init` always runs and creates `gam-ai-memory/` or completes an existing one; otherwise print its hint line and name `/gam-ai-memory init` as an open step in the summary (P-DOC-12).

The templates are the reusable versions of the `gamaiconcept` originals; that project remains their reference implementation for everything except the goal, human-readability, team, git-host-workflow, merge-policy, and model-setting rules added here (the knowledge templates of gam-ai-knowledge, CONTEXT-MAP, `.markdownlint.jsonc`, `gam-engineering/`, `claude/settings.json`, `claude/hooks/`, `agents/`, and the `gitlab/` and `github/` templates are new).

## Footprint

Part of step 2 (QA0045–QA0053, [README: Footprint](../../gam-engineering/README.md#footprint-tracked-stealth-minimal)). `tracked` keeps everything in git and changes nothing below. `minimal` runs the same setup, but git keeps no trace of it except one marked block in `.gitignore`:

1. Right after the answer, before any commit: copy [footprint.mjs](../../gam-engineering/templates/gam-engineering/tools/footprint.mjs) and [project-settings.mjs](../../gam-engineering/templates/gam-engineering/tools/project-settings.mjs) to `gam-engineering/tools/`, write `env.GAM_ENGINEERING_FOOTPRINT` = `minimal` into `.claude/settings.json`, and run `node gam-engineering/tools/footprint.mjs block`. It writes the block with every path setup creates (the gam- folders, the root files, `.claude/settings.json`, in a skill repo also the deploy launchers) and leaves out any path git already tracked. `git status` must then list no gam file.
2. The pipeline location is `local` (A5): [Pipeline](pipeline.md) does not ask it and writes no host CI file, since a host could not find the ignored checks. The chat export is `local` (A11): the AI chat export round does not ask the mode. No `prepare` script is added to `package.json` and nothing is added to `README.md`, since a clone gets no gam file to install.
3. The setup commit holds only `.gitignore` (and the project's own files, if any). Everything else of this setup stays on disk, ignored.
4. When the AI chat export round answers the project kind `student`, minimal is not allowed (P-TEAM-6, A3): the footprint becomes `tracked`, the block is removed from `.gitignore`, and this is stated as an assumption `A<n>`.

`stealth` is not offered here; an existing project moves there with [`migrate stealth`](migrate-stealth.md).

## AI chat export

Part of step 10 (P-TEAM-6, P-GRILL-2): the export is the record of every question round, so every project gets it. Copy [templates/gam-engineering/tools/prompt-export.mjs](../../gam-engineering/templates/gam-engineering/tools/prompt-export.mjs) to `gam-engineering/tools/`, and with it [templates/gam-engineering/tools/session-recover.mjs](../../gam-engineering/templates/gam-engineering/tools/session-recover.mjs) (reads a session that ended without a handover; run by hand, or proposed by [detect.md](../../gam-engineering/references/detect.md)). Copy [project-settings.mjs](../../gam-engineering/templates/gam-engineering/tools/project-settings.mjs) with them (the two settings layers, P-TEAM-2), and make sure `.gitignore` holds `.claude/settings.local.json`. Ask one `Q<n>` for the project kind: **student** (a student project: everything is committed), **teacher**, or **normal**; this is separate from solo or team. For `student`, write `commit` without a question. For `teacher` or `normal`, ask in the next `Q<n>` where the exported chats stay — **local** (only on each computer, `docs/prompts/` in `.gitignore`; recommended and the default) or **commit** (into the repo). Write `env.GAM_ENGINEERING_PROJECT_KIND` and `env.GAM_ENGINEERING_PROMPT_EXPORT` to `.claude/settings.json` (P-TEAM-6). With git, run `node gam-engineering/tools/prompt-export.mjs install-hook` yourself, never ask the developer to (it sets `core.hooksPath .githooks` or appends to the hook a project already has, keeping every other line — gam-ai-memory's `# agent-memory:hook` line then sits in the committed hook and reaches every clone — makes the hook executable, and stores the GitHub or GitLab user name in the local git config), and check that `core.hooksPath` points to the hook folder and the active `pre-commit` holds the marked line. If it prints `prompt-export: username unknown`, ask one `Q<n>` for the user name and set it with `install-hook --username <name>`. Only if the command cannot run (no Node 22.13, refused), name the reason and the command for the developer to run. Each clone needs it once: when `package.json` has no `prepare` script, add `"prepare": "node gam-engineering/tools/prompt-export.mjs install-hook"`, stated as an assumption `A<n>`; otherwise name the command in `README.md`. Copy the section *AI chat export* of [templates/CLAUDE.md](../../gam-engineering/templates/CLAUDE.md#ai-chat-export) into every agent instruction file the repo has (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.cursor/rules/`), replacing an older copy of the section instead of adding a second one; without any, `AGENTS.md` is created with it. Without git there is no hook; `stopp` runs `export`. With **commit**, record the check `{ "kind": "custom", "language": "", "tool": "node gam-engineering/tools/prompt-export.mjs check-growth", "threshold": "", "native": false, "ciImage": "node:24" }` in `gam-engineering/pipeline.json` (it only warns). Name in the summary that in a school project the school management decides whether students' chats may stand in a public repo.

## Line endings

Part of step 10 (P-GIT-12, Q447–Q452): with git, every project gets LF as its one line ending, so no edit by a script or an agent flips a file between LF and CRLF. Each file below is created when it is missing; when it exists, add only what it lacks and keep every other line or entry.

1. `.gitattributes`: each line of [templates/gitattributes](../../gam-engineering/templates/gitattributes) that the file lacks (`* text=auto eol=lf`, and `*.cmd`, `*.bat`, `*.ps1` with `text eol=crlf`). The `*` line comes first, so the three specific lines win.
2. `.editorconfig`: [templates/editorconfig](../../gam-engineering/templates/editorconfig) (`root = true`, `[*]` with `end_of_line = lf` and `insert_final_newline = true`, `[*.{cmd,bat,ps1}]` with `end_of_line = crlf`). No indentation or charset settings are added (Q449).
3. `.vscode/settings.json`: the keys of [templates/vscode-settings.json](../../gam-engineering/templates/vscode-settings.json) (`files.eol` as LF, with the `[powershell]` and `[bat]` overrides as CRLF) merged into the file; the other entries and comments stay. The file is made even for a project without VS Code files, since it does no harm to another editor (A4). Where `.gitignore` ignores `.vscode/`, change that line to `.vscode/*` and add `!.vscode/settings.json` below it, so the setting is committed; git cannot re-include a file of an ignored folder, only of an ignored folder's contents.
4. `gam-engineering/tools/eol-check.mjs` is copied with the other tools, and the check of kind `eol` is recorded in `gam-engineering/pipeline.json` when [Pipeline](pipeline.md#line-ending-check) writes it (the catalog entry is recommended, so the checks pop-up offers it, Q455).

5. `.worktreeinclude`: the lines of [templates/worktreeinclude](../../gam-engineering/templates/worktreeinclude) the file lacks (`CLAUDE.local.md`, `.claude/settings.local.json`, `.env`, `.env.local`), so Orca and Claude Code copy these git-ignored files into every new git worktree ([Parallel sessions](../../gam-engineering/references/parallel.md#orca), P-WS-13). In stealth mode also `orca.yaml` from [templates/orca.yaml](../../gam-engineering/templates/orca.yaml): the gam- folders under `worktree.sharedDirectories`, merged into an existing file entry by entry. When T3 Code is used on the computer (`~/.t3` or `T3CODE_HOME` exists) or the developer asks for it, also `t3.json`: `node gam-engineering/tools/worktree-setup.mjs --t3-json t3.json` merges the script of [templates/t3.json](../../gam-engineering/templates/t3.json) ([T3 Code](../../gam-engineering/references/parallel.md#t3-code)); an existing script with `runOnWorktreeCreate` stays and is named in the summary.

A new project has no committed files yet, so there is nothing to renormalize; its first commit is LF already. An existing project follows the row *Line endings LF* of [Migrating the tooling](migrate-tools.md), which also renormalizes the files that are committed, unless an open branch changed one of them: the row then waits (`gam-engineering/tools/eol-branches.mjs`) and the next `migrate tools` checks again.

## Worktree tooling

Part of step 10 (P-WS-13): with git, every project gets the script that makes a new worktree ready to work in ([Ports, data, and tests in a worktree](../../gam-engineering/references/parallel.md#ports-data-and-tests-in-a-worktree)).

1. Copy [templates/gam-engineering/tools/worktree-setup.mjs](../../gam-engineering/templates/gam-engineering/tools/worktree-setup.mjs) [templates/gam-engineering/tools/install-detect.mjs](../../gam-engineering/templates/gam-engineering/tools/install-detect.mjs), and [templates/gam-engineering/tools/worktree-number.mjs](../../gam-engineering/templates/gam-engineering/tools/worktree-number.mjs) to `gam-engineering/tools/`; the script imports the other two, and `prompt-export.mjs` takes the worktree number from `worktree-number.mjs`. Copy [templates/gam-engineering/tools/parallel-check.mjs](../../gam-engineering/templates/gam-engineering/tools/parallel-check.mjs) there too: the report of which program files force serial work, called by `architecture review` and `sweep` (P-ARCH-5). `gam-engineering/parallel.json` is not written; a project adds it by hand.
2. Add the lines of [templates/gitignore](../../gam-engineering/templates/gitignore) (`*.code-workspace`) to `.gitignore` when no existing line covers them; create the file if it is missing.
3. Ask once, as its own `Q<n>` in the round in which [Pipeline](pipeline.md) asks for the test command: which variables of the project's env file hold ports and which hold the test database. Read `.env.example` and `.env` first and offer what they hold as multi-select options (`PORT` and every key ending in `_PORT` for ports; `DATABASE_URL` and every key ending in `_DATABASE_URL` for the database), the found ones recommended, with **None** as the choice for a project without such variables. Write `gam-engineering/worktree.json` (`ports` with the value found as the base, `suffix` with the database variables) only when at least one variable is named, and state the result as an assumption `A<n>`; otherwise write no file, and the script only copies and installs.

## Parallel tests

Part of the test question of [Pipeline](pipeline.md#parallel-tests) and of the quick flow's short test (P-WS-13): when the project runs tests, propose the test command in its parallel form and let the developer confirm or replace it. The proposal is text; no script decides it. `node --test` already runs files in parallel and is proposed unchanged; `vitest run` (never the watch mode); `jest --ci`; `pytest -n auto` only when `pytest-xdist` is among the project's dependencies, otherwise `pytest`. A project with its own test script (`npm test`) keeps it unless the script runs a watch mode.
